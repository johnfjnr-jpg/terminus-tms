# Terminus Management System - design principles

Single DC: `Terminus Ops.dc.html`, titled "Terminus Management System" in-app. Terminus Design System tokens/components throughout. Sidebar wordmark: "Management System" label under the logo, with the M and S in bright white (`var(--terminus-white)`), rest dimmed (`var(--text-faint)`), 14px mono.

## Admin pattern
Admin is the "background data" configuration surface for the whole app. Every admin sub-area (Data Objects, Picklists, Workflows, ...) follows the same list-detail layout:
- Left rail (~200px card): pick the item (object / picklist / workflow). Selected item highlighted with `var(--surface-card-hover)` bg + `var(--accent)` text.
- Right panel (flexible card): configure the selected item's children (fields / values / stages).
- Each child row: reorder via ▲▼ (dimmed at list ends), inline Edit → text input → Save, delete via ✕.
- Bottom of list: a text input + "Add" button (secondary Button variant) to append a new child.
- Admin tabs (General / Data Objects / Picklists / Workflows / Taxonomy / Base Costs / Users / Documents) use the same underline-tab style as the HR module tabs, 14px inter-tab margin so all seven fit the content column.

## Admin data model built so far
- Data Objects tab: Contacts (9 mandatory fields + optional Notes; Industry and Source fields reference picklists), Test Beds (41 fields grouped into 8 sections - Terminus Reference, Executive Summary, Site Details, Key Dates, Installation Details, Test Bed Contacts, Use Case Selection, Test Bed Documents; section headers render inline in the flat field list), plus Leads (13 fields, top of funnel, including City - held for search), Terminus Staff (6 fields), and a stub Inventory Units object.
- Opportunities object (40 fields, 9 sections): Terminus Reference (Opportunity Reference is machine generated on creation by the same rules as the Test Bed reference, immutable for life or carried over when converting from a test bed; Lead/Commercial/Technical/Legal Authority from Contacts; Industry/Region/Country defaulted from Contact; Status from Workflow Engine), Executive Summary (description, timestamped Notes showing last 2 records latest-first, Opportunity Type = Terminus Led or Tender), Customer Details (Account - the customer account, defaulted from the contact account, edited from a dropdown of accounts on file or "+ New account"; Customer Lead / Technical / Commercial / Legal / IT-Security Buyers from contact list, plus a separate Commercial Address for Proposal), Key Dates (Date Created, Est/Actual Close Date, Est/Actual Go Live, Contract Duration (Months), Age as a calculated days-from-created value, Est Close Date move - the date is editable and a reason is mandatory, written to Notes as a timestamped record), Installation Responsibility (4-option picklist; Per Unit reveals cost-per-unit, Lump Sum requires a contractor price captured in the proposal workflow), Hardware Costs (USD / Unit), Installation Costs per Unit, Hosting Costs per Unit / Month - all ten cost lines mirrored from the Base Cost Data object and read from it when the opportunity is created, Opportunity Documents (references the shared Documents library). Admin field rows carry an optional `rule` string rendered as a dimmed second line under the field name - field names stay short, the rule holds the logic. Data objects carry an optional `description` replacing the default "Fields captured for every X record." caption.
- Base Cost Data object: the ten cost lines (Hardware / Installation per Unit / Hosting per Unit per Month) held as the maintained master, described as "The default costs associated with the Terminus Platform."
- Payment terms admin: a Payment Structure picklist (Single phase / Two-phase / Hybrid), an Invoicing Frequency picklist (Annual in advance / Monthly), a Loan Repayment Method picklist (Straight-line / Declining balance amortisation, used by Opportunities → Financing) and a Project Milestone picklist (Contract start, Hardware delivered to site, Installation complete, Commissioning, Go live, Final acceptance) feed the Opportunity Payment Terms tab, and the Opportunities data object carries a Payment Terms section (Payment Structure, Recovery Period (Months), Hardware Milestones, Hosting Invoice Schedule, Invoicing Frequency) and a Financing section (PO Factoring, Loan Principal, Monthly Interest Rate (%), Loan Term (Months), Repayment Method).
- Picklists tab: Lead Source, Industry (14 sector values, each carrying a maintained 6 character `code` used by the record reference - editable inline next to the value, shown as a dimmed mono second line when not editing; a picklist opts in via `hasCodes: true`), Region (Americas/Europe & UK/Middle East/APAC), Opportunity Stage (Qualification/Needs Analysis/Proposal/Proposal Submitted/Negotiation/Closed Won/Closed Lost), Lead Status (Unqualified/Converted), Installation Responsibility (4 values), Opportunity Outcome (Won/Lost, applies when stage = Closed), Site Ownership, Installation Environment, Installer.
- Taxonomy tab: Industry → Classification → Use Case tree (Smart City and Manufacturing and Industrial populated; other industries empty). Referenced by Test Beds → Use Case Selection.
- Documents tab: shared template library (NDA, DPIA, Site Assessment Report, Partnership and Test Bed Agreement, Installation and Commissioning Sign off, Test Bed Review Document, Reseller Agreement, EULA, Data Processing Agreement, Opportunity Assessment, Risk Assessment, Proposal Document, Terminus Contractual Terms), each with one centrally-maintained URL, referenced by every Test Bed and Opportunity record. On record creation the user selects the template from its URL and saves the modified document into the folder created for that record. Two entries have no template URL and instead carry a `source` note ("Supplied by contractor after site visit"): Contractor Site Visit Report and Contract Proposal.
- Workflows tab: Test Bed (6 stages, Qualification→Decommissioning, several with sub-stages e.g. Planning → Pre-Site Assessment/Site Assessment) and Opportunity (5 stages, last stage "Closed" carries a Won/Lost outcome qualifier badge). Every stage/sub-stage has its own Docs to be completed, Exit Criteria, and Required Approvals (Technical/Commercial/Legal).
- Users tab: the Terminus staff list and their system access. Left rail lists staff (green dot = active, job title as a dimmed second line) with name + job title inputs and "Add user" beneath; right panel carries the six user fields - Name, Job Title, Project Role, Approval Role, Email, Phone - plus an Active/Disabled toggle. Project Role (System Administrator / Sales / Delivery / Engineering / Finance / Legal / Read Only) sets what the person can do; Approval Role (None / Technical / Commercial / Legal Authority) is exclusive - assigning one clears it from whoever held it - and stage-exit approvals read the approver name from whoever holds the matching Approval Role, replacing the former Approval Authorities panel on the General tab.
- General tab: a "Viewing as" switcher for testing approvals as different users, plus team, region, ticket-colour and notification settings. The Approval Authorities panel has been removed - approvers now come from the Users tab roles.
- Base Costs tab: cost maintenance for the three separately-manufactured hardware lines (SafeSight / Air Quality Monitor / HEMIR), each with its own batch series (SSB / AQB / HMB prefixes). Left rail picks the hardware line; right panel lists its last 3 batches newest-first (green dot = current = newest), each with effective-from date and run size as a dimmed second line under the Batch ID, and the unit cost. Selecting a batch lets its unit cost be edited; "Add batch" creates a new batch carrying the previous unit cost forward. Every change to a hardware unit cost must belong to a new Batch ID. Installation and hosting costs sit in a separate card below, not batched - each carries a last-changed timestamp that updates on edit.
- All admin lists (fields, picklist values, workflow stages/sub-stages/criteria/approvals, document templates) support inline edit, delete, add via bottom input, and up/down reorder.

## Record references
Test Beds and Opportunities share one reference format and one sequence: `TT-CCC-INDCDE-NNN` - `CCC` a 3 letter country code, `INDCDE` the maintained 6 character `code` on the Industry picklist value (falling back to the first 6 letters of the value if no code is set), `NNN` a 3 digit sequence counted per country+industry combination across BOTH object types (e.g. TT-GBR-SMARTC-002). A number is issued once and never reused, even if the record is deleted - `nextRecordRef()` keeps a highwater mark per prefix as well as scanning existing refs. Records carrying a short `sector` label map back to a picklist industry via `sectorToIndustry()` before the code is derived.

## Sales funnel logic
- Leads are the top of the funnel: raw, unverified interest. Step 1 create the lead, step 2 qualify it (budget and need). Qualification IS the conversion.
- Qualifying a lead creates the Contact record from the lead data, sets the lead status to Converted and drops it out of the Leads list, then lands the user on Contacts. Every contact field must be completed first - the move is blocked with an amber message naming the missing fields.
- Test Beds and Opportunities are created from a Contact, never from a lead. There is no Convert action on the lead list row or the lead detail page.
- Lead Status is Unqualified, Parked or Converted (the Qualified chip is the action that converts).
- Contacts carry an Account field - the company record the contact belongs to, defaulted from the lead company at qualification and editable on the contact. In the Contacts list it sits as a dimmed mono second line under Company (column headed "Company / Account") rather than its own column - eight flexible tracks overflow the content width. Editing Account on the contact detail opens a dropdown of the accounts already on file plus a "+ New account" option, which swaps the dropdown for a text input so an entirely new account can be typed.
- Leads sit above Contacts in the nav. Lead cards lead with the person's name plus the status badge on the same line, company and role on the second line. Clicking a lead opens a full-page detail view (fields + summary panel, notes history at the bottom, newest first, each note timestamped with its author).

## Action required (overdue activities)
Every user landing on the Dashboard sees an "Action required" panel above the metric tiles listing activities that have fallen out of date - the things that get forgotten. Amber-bordered, hidden entirely when nothing is overdue, one row per item: activity kind (104px), the record it belongs to, its due date, and how late it is. Clicking a row opens that record. The first activity type is Lead follow-up (a Parked lead whose follow-up date has passed); the row shape is deliberately generic so other overdue activities (stage exits, contractor re-evaluations, unsigned documents) can be added to the same list.

## Lead detail editing
Fields are click-to-edit: clicking the value highlights it and turns it into an input or picklist - there is no Edit link. Several fields can be open at once; a bar under the field grid shows how many are open, carries one optional "Note on what changed", and one Save changes / Cancel pair. Each open field carries a small dimmed ✕ to discard just that field. Saving writes one timestamped note per changed field, with the optional note appended to the first. Save is blocked with an amber message if a mandatory field is blank or nothing has changed. Summary edits the same way and joins the same save.

## Lead status and parking
Qualifying a lead requires every field except Follow-up to be completed - the move is blocked with an amber message under the status chips naming what is still missing. Moving back to Unqualified, or parking, is never blocked. Lead Status is Unqualified, Parked or Converted. Status is set on the lead detail page from a chip selector (Unqualified / Qualified / Parked) under the header, with a dimmed line beside it reading "Qualifying creates the contact and closes the lead" - there are no Park or Convert buttons in the header row. Picking Qualified creates the contact, writes a timestamped note ("Lead qualified. Budget and need confirmed. Converted to contact X.") and moves the lead to Converted; picking Parked opens the follow-up date field and refuses to save without one, then notes it; picking Unqualified reactivates a parked lead, clears the date and notes that too. Unqualified and Parked leads appear in the Leads list; Converted ones drop out. Once the follow-up date passes, the lead shows in Action required on the Dashboard until it is followed up, re-parked or converted.

## Opportunities list
Opportunity name on the left taking the remaining space, everything else anchored right and right-aligned with the header: Stage (118px), a combined meta column (148px) reading "probability · age · close date", Value (56px), Update toggle. The name is capped at 40 characters and allowed to wrap, with the full text on hover; stage and meta cells still ellipsis with a hover title. Weighted Value is not repeated on rows - the totals sit in the metric tiles above. Dates read "30 Oct 26"; the "+N moves" count lives in the detail view only. Header and rows are separate grids, so every right-hand track must be a fixed px width (widths above are measured against worst-case content). Row padding 7px.

## Metric tiles
Money is shown in USD ($) everywhere, never GBP. On rows, values align to the record-name baseline, not the row centre. The Opportunities metric row uses short labels (Won, FY / Wtd, FY / Unwtd, FY) to fit the compact tiles; the Dashboard keeps the full wording.
All metric tiles (Dashboard and the Opportunities metric row) are compact single-line: label left, value right, no stacked block - roughly half the height of a stacked tile. Every value tile carries a hover popup listing the opportunities behind the number - name, industry, contract value - with weighted tiles showing weighted amounts. Popups anchor left on left-side tiles and right on right-side tiles so they never collide with the sidebar.

## Opportunity detail
Full-page tabbed view (same pattern as Test Bed detail, not a modal), opened by clicking a pipeline card. Header carries stage dot + stage name (+ Won/Lost badge when closed), company, sector and reference on the left, value + probability on the right. Four tabs:
Editing follows the Lead pattern: click a field value to open it in place (caret lands where you clicked, green border only once the value actually differs), several fields can be open at once across the tab, and one Save / Cancel pair plus a change count sits on the tab line. Each open field carries a dimmed ✕ to discard just that field. Saving writes one timestamped note per changed field. The header block (stage, company, reference, value) and the tab row are sticky, so they stay in place while the tab content scrolls.
- Reference: reference fields (Opportunity Reference, Terminus Lead, Commercial/Technical/Legal Authority, Industry, Region, Country, Status) with Key Dates as a right-hand panel (Est. Close Date carries an Edit action: it opens a date field plus a mandatory reason, blocked with an amber message if the reason or date is missing or the date is unchanged; saving writes a timestamped note "Est. Close Date moved from X to Y. <reason>" to the opportunity Notes and updates the date), then Executive Summary (with Opportunity Type in the label) and Notes (last 5, latest first, timestamped with author) full width below. Every reference field is inline editable via an Edit link on the row (Terminus Lead, Commercial/Technical/Legal Authority, all Customer Details rows, Actual Close Date, Est. Go Live, Actual Go Live, Contract Duration (months)) - the exceptions, which are read only, are Opportunity Reference, Industry, Region, Country, Status, Date Created and Age. Person fields (Terminus Lead, Commercial/Technical/Legal Authority, Customer Lead, Technical/Commercial/Legal/IT-Security Buyer) are never free text - editing opens a dropdown of existing contacts plus a "Create new contact..." option, which opens the contact dialogue over the current page and, on save, returns to the same page with the new contact selected in that field. Other fields edit as a text input with Cancel/Save, blocked with an amber message if the value is empty or unchanged; saving writes a timestamped note "<Field> changed from X to Y." to the opportunity Notes, authored by the current user.
- Commercials: a persistent Deal Summary (USD) matrix sits at the top of the tab (rows Cost / Margin (dollar value) / Price / WHT against columns Hardware / Hosting (over the contract term) / Installation / Total), above four sub-tabs in the same underline-tab style: Hw / Hosting Setup, Installation, Structural Terms, Payment Terms. Currency is carried in the column heading, never in front of each value, across all Commercials tables; margin defaults to Target Margin and is editable per line, price = cost / (1 - margin).
  - Hw / Hosting Setup: Units Required, then the Unit cost and warranty and Hosting (per month) pricing panels (Item / Cost (USD) / Margin % / Price (USD) with a Total row) and the hardware and hosting cost lines read live from Base Cost Data - hardware lines show the current batch ID.
  - Installation: Installation Responsibility rows (second row label varies - Cost per Unit for Per Unit, Lump Sum Contractor Price for Lump Sum), the Installation pricing panel, and the installation cost lines. A lump sum deal shows a one-line summary of the lump cost, its price, and that it is carried into the Deal Summary, deal sheet and cash flow.
  - Structural Terms: three panels - Margin and Warranty (Target Margin % first, then Warranty %, achieved-margin readout beneath), Currency (Bid Currency, Proposal Currency, both dropdowns defaulting to USD, plus % Currency Contingency), and Tax Adjustments (Withholding Tax %, GST %, plus the Gross up toggle button). Currency fields are captured but not yet applied to the pricing maths. Below them the Deal sheet (USD) over the contract: revenue, the hardware / installation / hosting cost lines, PO factoring interest, WHT borne or grossed up, total cost, gross margin, then the invoice reconciliation (price to customer, GST passed through, WHT deducted, net receipt). This replaces the former P&L tab.
  - Payment Terms: the three payment structures plus invoicing frequency (see Payment structures below), the per-unit monthly fee table (During recovery period / Standard hosting, one column per product line with units in the deal), the milestone table for hybrid, and the year schedule. Warranty units = total units x Warranty %, rounded UP to a whole unit, costed at average hardware unit cost. Gross up sets invoiced value = net / (1 - WHT %); GST is added to the invoice and passed through. Cash flow sits at the bottom of this tab (see Financing below).
  - Customer Details sits in the Reference tab's right-hand panel, under Key Dates.
- Documents: shared template library, same list as Test Beds.
- Stage & Approvals: identical conventions to the Test Bed tab - 3-column table (Stage / Exit criteria / Approvers), stage name + probability under it, green dot = current, muted = completed, faint + 0.55 opacity = upcoming; 14px ring radios clickable only on the current stage and only for the matching approval authority. Stages come from the Opportunity workflow.
Sample data authored for op1 (Transport for Greater Manchester, Qualification), op6 (Network Rail LNER, Negotiation / Review), op7 (Leeds City Council, Closed Won); others show dashes until configured. Pipeline column stage maps to a workflow sub-stage (lead→Qualification, demo→Needs Analysis, proposal→Proposal, closed→Closed) unless the record carries its own `subStageKey`.

## Asset Management - Product Capability Catalog (Stage 1)
Top-level nav item "Asset Management", sitting between Inventory and Contractor Management. Stage 1 is the product capability catalog only - the versioned bill of materials for every hardware product Terminus manufactures. Stages 2-5 (component batch tracking, serial number records, assignment history, internal IT asset register) are out of scope and have no stubs.

**Data model.** Device Type (name, description) → Configuration (belongs to a device type, has a name) → Configuration Version (number, effective date, status Draft/Approved/Superseded, approver + timestamp) → Configuration Version Requirement (component type + quantity). Component Type is one master list shared across all device types, maintained inside the module itself.

**Screens.** Two tabs in the same underline-tab style as Admin: Device types and Component types.
- Device types tab drills down: device type list (name / description / configuration count) → configuration list for that device type (name / current version / status / version count, with a "← Device types" breadcrumb) → full-page Configuration detail overlay (`position:absolute;inset:0` + `max-width:1080px;padding:32px 48px 60px`, same pattern as Test Beds and Opportunities). Entering the module always resets to the device type list - `setModule` clears `selectedDeviceTypeId`, `selectedConfigId` and `assetsTab`.
- Component types tab is the master list: inline edit, add via bottom input, delete blocked (and the ✕ dimmed) while the component is used by any version, with a "Used in N versions" column.

**Configuration detail.** The version timeline IS the screen, not a tab: oldest to newest, each version a block on a left rail with a status dot. Approved = accent dot and accent 2px rail, full opacity. Draft = amber dot and amber rail. Superseded = faint dot, hairline rail, 0.55 opacity and muted body text, and reads "Locked" where a draft carries actions. Each block lists its requirements as component type + `Nx` quantity. Header carries the device type, configuration name, current approved version, version count and the new-version action.

**Immutability.** Approved and Superseded versions are read only - no edit affordance at all, only a "Locked" label. Drafts carry Edit requirements / Discard / Approve. Approve opens an inline amber confirmation stating that approval locks the version permanently; only the holder of the Technical Authority approval role (Users tab) can complete it, others see the authority's name instead of the confirm button. Approving stamps approver + timestamp and demotes the previous Approved version to Superseded. A configuration can only have one open draft at a time.

**Requirement builder.** Modal over the configuration detail. Effective date plus rows of component type (dropdown from the master list) and quantity, an "Add component" action and per-row ✕. A new version pre-populates from the current approved version, never from blank. Validation blocks empty rows, non-positive quantities, duplicate component types and a missing effective date. Saving always produces a Draft.

**Sample data.** SafeSight (Outdoor 3 versions, Indoor 1, Outdoor (Long Range LiDAR) approved v1 + open draft), HEMIR (Standard approved, Extended Array draft), AQ Sensor (Standard approved). A SafeSight unit carries exactly ONE of each sensor - 1x optical, 1x LiDAR, 1x thermal imager. Variation between configurations comes from the component TYPE (Long range LiDAR instead of LiDAR), never from the quantity. Version changes are substitutions or additions (Jetson chip → Nvidia perception chip; adding an Edge storage module), not quantity bumps. HEMIR is genuinely an array, so 8x Infra red is correct there.

**Copy.** Precise Terminus terminology - "Configuration", "Configuration Version", "Component Type", never "variant", "revision" or "part type". Sentence case in all labels and headings. No em dashes.

## Asset Management - the rest of the module
Eight tabs in one underline row, in order: Fleet, Device types, Component types, Component batches, Build batches, Components, Devices, Perception layer. The page heading and subtitle follow the selected tab ("Fleet dashboard", "Product capability catalog", "Batch tracking", "Component and device records", "Perception layer") - never leave catalog wording over a batch or device screen. Entering the module resets to the Fleet tab and clears every drill-down selection. The standalone Inventory nav item was removed; the Devices tab replaces it.

### Batch tracking (Stage 2)
- Component Batch: component type, manufacturer, batch ID, order confirmation ref, quantity, status (Ordered / In Transit / Received / QC Passed / QC Rejected), order and received dates. Status is a click-one-of-five control on the detail page, not a formal action; moving to Received or either QC state stamps the received date if empty.
- Build Batch: assembly partner, batch ID, configuration version, quantity, build date. Detail carries a "Built against" panel with an "Open catalog record" action that jumps to the Stage 1 configuration.
- Manufacturers and assembly partners come from Contractor Management, filtered by a `capabilities` field (`Component supply` / `Device assembly`); contractors without the field default to `Installation` and appear in neither dropdown. Suppliers added: Vantage Optics, Kestrel Sensing, Delta Board Systems, Halden Enclosures; assembly partner: Argent Assembly.
- Both detail pages share one document row: pick a document type or add a new one inline, paste a Google Docs URL, attach. Nothing here is locked or versioned - this module reads deliberately lighter than the catalog. Batch to batch traceability is NOT tracked; it is derived at serial level.
- The cost batches in Admin - Base Costs are a separate concept and stay separate. No link between them.

### Component and device records (Stage 3)
- Devices are generated automatically when a Build Batch is logged, one per unit, serialled from the device type prefix (`SS-` / `HM-` / `AQ-`, 5 digits). Never created by hand.
- Device statuses: In Stock, Shipped, Installed, Live, Recalled, Under Repair, Reallocated, Retired. Live = accent, Recalled and Under Repair = amber, Retired = faintest.
- "Delivery site" and "live coordinates" are distinct fields, both always visible. Delivery site is read only and inherited from the linked Opportunity or Test Bed; live coordinates are editable lat/long.
- Bill of materials validation is derived at display time from the device's configuration version: required vs assigned per component type, with complete / short states. It is a live indicator, never a blocking gate.
- Reallocation names both ends of the move before confirming ("SS-00412 moves from A61 Corridor (Test Bed) to ..."), a soft warning not a hard block. Setting a device to Recalled opens a panel offering to create the replacement device carrying the same configuration and link, and closes the recalled unit's link - a recalled unit never returns to service with the same customer. "Recall" is the only word for this; never "return" or "reallocate".
- Serial entry accepts a pasted list (line breaks, commas, tabs, stray whitespace all tolerated) or one at a time, in the same modal, and reports how many were logged and how many were already on file.

### Assignment history and reallocation (Stage 4)
- Unassigning a component requires a reason from a fixed set, used verbatim: Warranty Swap, Reallocated to Demo/Test Bed, Failed/Faulty, Decommissioned. No destination is asked for; the component returns to the pool and the device's BOM shows the shortfall immediately.
- History runs both ways off the same data: a Component history timeline on Device detail, a Device history timeline on the Component record. Both follow the Stage 1 version-timeline treatment - dot on a rail, current entry accent, closed entries 0.62 opacity. A live row shows "Assigned <date>" plus a "Current" marker only; unassigned date and reason appear on closed rows alone. Never render "Unassigned Current".
- Component records open from the pool list and from the device's serial list.
- Perception layer version is held against the CHIP (Jetson chip, Nvidia perception chip), not the device, so history travels with the chip. Always "perception layer version", never software or firmware.
- The Perception layer tab is a bulk update: filter by device type / configuration / current version, tick devices (units with no chip are not selectable), enter the version, Review shows a summary naming the count and the from and to versions, then Apply writes one entry per chip, dated and attributed. Seeded at 3.2 with three SafeSight units on 3.4.

### Fleet dashboard
- One dashboard, never separate pages per cut. Group by (Opportunity / Test Bed, Country, Build batch, Component batch) is a chip row and is visually separate from the filters (status, device type, configuration) - the two do different jobs.
- Summary layer is four clickable cards, unaffected by group by: incomplete bill of materials, overdue a status transition, perception layer spread, devices by status. Clicking one filters the table below and shows a clearable "Showing ..." bar. No charts - simple counts only.
- Detail layer is grouped rows, each group header showing device count and flagged count. Flagged rows sit on a faint warm tint with one pill per reason, so a device with two problems shows both. Rows open the device record.
- Overdue is derived from the latest status-bearing date on the device (go live, installed, delivered, then build date), against a single global threshold held in Admin - General - Asset management, default 28 days. Live and Retired devices are never overdue. Flags use the amber `#e0824a` at low opacity, never a second accent colour.
- The module adds no stored entities; everything is derived from Stages 1 to 4.

## Use Case Curation (product development intake)
Top-level nav item "Product Management", between Opportunities and Asset Management. Intake and review process that feeds the Admin - Taxonomy tree; the tree itself is unchanged. Nothing is written to Taxonomy before Approval.

- Two tabs in the module: Use cases (list) and Review queue. Heading and subtitle follow the tab.
- List: status chip row plus Industry / Source / Product selects and Clear, a count line, and a List / Grid toggle. List columns `minmax(140px,1fr) 132px 120px 100px` (Use case with products and date on a dimmed second line / Industry / Classification / Status). Grid is 3 cards per row.
- Review queue: Submitted and Review items, oldest first, columns `110px minmax(0,1fr) 112px` (Submitted / Use case with industry and submitter on a dimmed second line / Status), plus a line naming whether the current user may act.
- The content column inside a Card here is about 554px, so fixed tracks plus gaps must stay under that or the flexible title track resolves to 0px. Re-measure after any column change.
- Detail is a full-page overlay with sticky header and tab row: Reference, Objective and success, Technical scenario, Review and disposition, Attachments.
- Editing on Reference, Objective and success, and Technical scenario follows the Lead detail rules exactly: click a value to open it in place (green border only once it differs), several fields open at once, each with a dimmed ✕ to discard just that field, and one bar under the field grid carrying the open-field count, an optional "Note on what changed" and one Save changes / Cancel pair. Saving writes one timestamped history entry per changed field, with the optional note appended to the first; it is blocked with an amber message if a mandatory field (Title, Source, Objective, Problem addressed) is blank or nothing has changed. Fields are only clickable while the record is Draft or Submitted; Review, Approved and Rejected records are plain text. Product tags open as a chip toggle row, and each selected product carries its own target version field. Review and disposition is the reviewer's working form, not record fields, so it keeps direct controls saved by the workflow action.
- Workflow: Draft -> Submitted -> Review -> Approved, with Return for clarification (back to Submitted, requires review notes) and Rejected (requires a reason) off the Review stage. Approved and Rejected records are read only; Draft and Submitted are editable by the submitter.
- Roles: a new Project Role value "CTO or CEO" on the Users tab gates every review action (E. Varga, u6, holds it). Everyone else sees the record and the review notes read only, with a line naming the reviewer. Switch user via Admin - General "Viewing as" to exercise it.
- Industry, as submitted uses the existing Industry picklist plus a "New industry, needs review" option carrying a note. Industry, confirmed is set at Review; "+ New industry picklist value" takes a name and a mandatory 6 character code, then requires an explicit amber confirmation naming the system-wide effect before it is written into Admin - Picklists.
- Classification is free text at submission and constrained at Review to the classifications that exist under the confirmed industry, with "+ New classification" as the escape. When the industry has no classifications yet the submitted text stands and creates the branch on approval.
- Approval writes or updates the Taxonomy leaf under confirmed industry / classification, creating the classification if needed, with status Next Version when any target version is named and Roadmap-Unknown otherwise. It shows an amber confirmation naming the placement first, then stamps approver and timestamp and locks the record. Current is only ever set manually in Taxonomy after ship.
- Product tags are SafeSight / MetroSense / TrueShield AI / HEMIR, each with an optional freeform target version. There is no version registry; the field exists so the data is not lost.
- Every transition writes a timestamped history entry (right-hand panel on the Review tab). Submitter field edits are not noted.
- Attachments are document type plus a Google Docs URL, same shape as Build Batch documents, with inline "+ New document type".

## App shell (do not break)
Every module page lives inside one scroll container: `<div id="app-content-scroll" style="flex:1;min-width:0;overflow-y:auto;position:relative">`, a flex sibling of the 216px sidebar. Each page is an `<sc-if>` block inside it whose wrapper is `<div style="padding:40px 48px 60px">` (detail overlays: `position:absolute;inset:0` + an inner `max-width:1080px;padding:32px 48px 60px`). That 48px gutter is what makes every screen start at the same left edge (264px = 216 + 48) - never change it on one page only.

**Regression guard.** A single unbalanced `</div>` or stray `</sc-for>` anywhere in the template closes `#app-content-scroll` early; every page after that point renders as a flex sibling of the sidebar and drifts right by a different amount per screen. This has happened once (a leftover `</div></sc-for>` in the Lead detail field grid). After ANY structural edit to the template, verify tag balance before finishing: walk the file from the `app-content-scroll` line counting `<div` minus `</div>` - the depth must not reach 0 before the closing tag near the end of the page blocks (currently ~line 2900). If it drops to 0 early, the extra close tag is just above that line. Do not "fix" the symptom with padding or margins.

## Payment structures
Three options on the Opportunity Payment Terms tab, each combined with an invoicing frequency of Annual in advance or Monthly.
- Single phase: the total contract price - hardware, warranty, installation and hosting - is spread evenly across the full contract duration, so every month of the term carries the same fee. The recovery period is the contract duration and is read only.
- Two-phase: during the recovery phase, the hardware, warranty and installation price is pro rated across the recovery months and the monthly hosting fee is added on top. After the recovery phase, only the hosting fee is charged. Either phase is billed monthly or collected a year at a time in advance.
- Hybrid: hardware, warranty and installation are recovered through milestone invoices raised in set months (max 5, Month / Project milestone / % / USD, amber flag when they do not total 100%). Hosting sits outside the milestones, runs every month of the term, and follows the invoicing frequency. Layout is milestone table left, invoicing radios plus a vertical year schedule right.

## Financing and cash flow
The Cash flow block at the bottom of the Payment Terms tab models the deal month by month for the contract duration, with a sticky row-label column and one 88px column per month.
- Rows: Cash in (hardware recovery or milestone payments, hosting fee, PO factoring advance), Total cash in, Cash out (hardware, installation, hosting cost, factoring principal and interest), Total cash out, Net cash flow, Cumulative cash position. Negative values render amber, positive cumulative in the accent green.
- A flag line above the table reads either "Cash position stays positive throughout the term." (green) or names the peak shortfall and the month it falls in (amber). Hybrid deals whose milestones do not total 100% also carry an amber note.
- PO factoring is off by default and toggled per opportunity. Loan principal is calculated, not entered: the total hardware, warranty and installation cost, so the loan is sized against cost and not the marked-up price. Monthly interest rate defaults to 1.5% and is charged on the outstanding balance. Loan term defaults to the recovery period for two-phase deals and 12 months for hybrid; the advance lands in month 1 and repayment starts month 2, so the final instalment falls in month term + 1. Repayment method is straight-line (constant principal, falling payment) or declining balance (constant payment, shifting principal / interest split).
- Only the interest is a cost: it sits in the Hardware column of the Deal Summary and in the deal sheet, and reduces achieved margin. Principal repayment affects cash flow only.
- Cash flow follows the invoicing choice: annual in advance collects each 12-month window in the first month of that year (months 1, 13, 25...), monthly bills as it falls due. Hosting cost is always paid monthly on the cash-out side regardless of how it is invoiced.
- With no Contract Duration set on the Reference tab the table is replaced by a prompt to set it.
