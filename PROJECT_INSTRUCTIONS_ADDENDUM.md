# Addendum for the Terminus Management Portal project instructions

Paste this into the project instructions, under a new heading. It is written
to sit alongside the existing Project Philosophy and Working Style sections,
not to replace anything in them.

---

## Governing documents and current state

Four documents govern this project. They are deliberately separate because
they answer different questions, and collapsing any two of them has already
caused real rework.

| Document | Answers | Written by |
|---|---|---|
| `DESIGN_PRINCIPLES.md` | Why a decision was taken, and what it supersedes | By hand, updated the moment a decision changes |
| `PROTOTYPE_SPECIFICATION.md` | What `Terminus_Ops_dc.html` actually does, cited by line | By hand, from real citations only |
| `INTERACTION_STANDARDS.md` | What correct interaction behaviour means | By hand, specification only |
| `CURRENT_STATE.md` | What is configured and built right now | **Generated by `scripts/state-dump.mjs`, never by hand** |

`CURRENT_STATE.md` exists because design conversations happen in this chat,
away from the repo, and the facts that go stale between sessions are
factual rather than conceptual: gate rule contents, stage definitions,
approval tracks, writable-key allowlists, route inventory, record counts by
status. Those were previously reconstructed by hand at the start of every
round, which is slow and occasionally wrong.

### Rules for `CURRENT_STATE.md`

1. **Generated, never hand edited.** It carries a generation timestamp and
   the git commit SHA it was produced at. A copy whose SHA is not current
   is stale and is treated as untrusted rather than approximately right.
2. **It records what is, never why.** Reasoning belongs in
   `DESIGN_PRINCIPLES.md`. A generated file that starts carrying
   justification will drift, because nothing regenerates an opinion.
3. **Every value read from the live database or by parsing the real source
   file.** Never restated from another document.
4. **No secrets and no client data.** No environment variables, keys or
   tokens. Records are reported as counts by status, never by name or
   reference code. This file is uploaded into chat sessions.
5. **Tracked in git.** The diff between rounds is the configuration
   changelog, and is worth more than any single snapshot of the file.
6. **A round is not complete until it has been regenerated and its diff
   reconciled against that round's own phase list.** A change in the diff
   that no phase accounts for is a finding, not noise.

### How to use it in this chat

Upload `CURRENT_STATE.md` at the start of a session alongside the three
hand-written documents. Where it and a hand-written document disagree,
**`CURRENT_STATE.md` is right about what exists and the hand-written
document is right about what was intended**, and the disagreement itself is
usually worth investigating rather than resolving quietly. Several of this
project's most useful findings came from exactly that kind of mismatch.

### What this does not change

The separation between this chat and the repository is deliberate and stays
as it is. Chat does not read the codebase. That constraint is why decisions
get written down at all, and the written record is part of what makes the
system valuable as a business asset rather than just as internal tooling.
`CURRENT_STATE.md` closes the factual gap without closing that one.
